# PROJECT.md — BADAK AI Worker: Vision Intelligence Upgrade

## What We're Building

Replacing the existing OpenCLIP (tag/object detection) and BLIP (captioning) models in the BADAK AI Worker Python microservice with a single **Microsoft Florence-2-base** vision-language model backed by a **Helsinki-NLP/opus-mt-en-id** translation model.

The result: richer open-vocabulary tags, accurate English object detection, fluent Indonesian captions with real SPOK structure, name-aware caption injection when face cluster names are known, and built-in OCR — all running CPU-only without changing any existing API endpoints or response field contracts.

## Problem Being Solved

### Current limitations

| Component | Problem |
|---|---|
| OpenCLIP `get_tags()` | Zero-shot classification but against a hardcoded 117-item Indonesian tag list — still dictionary-bound |
| OpenCLIP `get_objects()` | Zero-shot classification against a hardcoded ~170-item English noun list — same limitation |
| BLIP `get_context_comprehensive()` | English caption generated by `blip-image-captioning-base`, then keyword-mapped to Indonesian phrases from a static dict. Falls back to "foto bersama" for anything unrecognised |
| BLIP Indonesian output | Not a real translation — template strings assembled from regex keyword matches |
| OCR | Not implemented at all |
| Caption personalization | Cannot use known face cluster names in captions |

### Why this matters

BADAK AI Worker is used to analyse Indonesian government/official photography. Tags like "foto bersama" as fallback, and objects limited to a dictionary list, produce poor search and metadata quality. The C# backend indexes these fields for search — garbage in, garbage out.

## Solution Architecture

### Models

| Model | Size | Role |
|---|---|---|
| `microsoft/Florence-2-base` | ~450 MB | Tags, objects, captions, OCR — single model for all vision tasks |
| `Helsinki-NLP/opus-mt-en-id` | ~300 MB | English → Indonesian translation for tags and captions |

Total new model footprint: ~750 MB. Existing InsightFace stays unchanged.

### New model files (drop-in replacements)

| New file | Replaces | Signatures preserved |
|---|---|---|
| `models/florence_model.py` | `models/openclip_model.py` | `get_tags()`, `get_objects()` |
| `models/caption_model.py` | `models/blip_model.py` | `get_context_comprehensive()`, `detect_school_age()` |
| `models/translation_model.py` | *(new shared utility)* | `translate(text) → str` |

### Florence-2 task mapping

| Method | Florence-2 task(s) | Output |
|---|---|---|
| `get_tags()` | `<OD>` + `<DENSE_REGION_CAPTION>` | Merge labels + region phrases → translate → Indonesian `List[str]` |
| `get_objects()` | `<OD>` | Label strings → deduplicated English `List[str]` |
| `get_context_comprehensive()` | `<MORE_DETAILED_CAPTION>` | Long English prose → name injection → translate → structured dict |
| `get_ocr()` | `<OCR>` / `<OCR_WITH_REGION>` | Flat text string or text+quad-bbox regions |

### Name injection in captions (new capability)

When face cluster names are known, `get_context_comprehensive(image, known_faces=[...])` uses `<CAPTION_TO_PHRASE_GROUNDING>` to locate face regions in the caption, then post-processes "a man"/"a woman" references to use real names (e.g. "Budi Santoso"). Falls back to generic descriptions gracefully when names are unknown.

### API changes (additive only, no breaking changes)

- `ProcessResponse.ocr` — new optional field (`null` by default, populated when `ENABLE_OCR=true`)
- `routes.py` — small addition to pass face cluster names into `get_context_comprehensive()`
- All existing fields (`tags`, `objects`, `context`, `context_detail`, `faces`) — unchanged shape

## Constraints

- **CPU-only required** — must work without GPU (slower is acceptable)
- **No API breaking changes** — existing C# backend must not need updates
- **No response field renames** — `tags`, `objects`, `context`, `context_detail` stay as-is
- **Model size budget** — total new models ≤ 4 GB (actual: ~750 MB)

## Out of Scope

- Changing InsightFace or the face clustering pipeline
- GPU-specific optimisations
- Changing any existing API endpoint paths or HTTP methods
- Adding new endpoints beyond the optional OCR field in ProcessResponse
- Dark mode, UI, or frontend work (this is a backend Python service)
